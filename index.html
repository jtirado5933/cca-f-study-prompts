Introduction

Studying for the Claude Certified Architect – Foundations exam? Anthropic published v1.0 of the exam guide. Below: what you're walking into, how to prep, eight prompts you can paste into Claude (attach the official PDF first), and domain-deep instructor prompts. Those domain sections are an updated revision of hoeem's original “Claude Architect” study prompts, realigned to the v1.0 CCAR-F guide (July 2026).

What you're walking into

  • 60 questions, 120 minutes: about 2 minutes per question.
  • Multiple-choice and multiple-response: each question tells you how many answers to pick. Much prep material still assumes one right answer.
  • 4 scenarios, randomly pulled from a bank of 6. You can't skip any.
  • Pass mark: scaled 720 out of 1,000. Score report breaks out % correct by domain.
  • Credential: valid 12 months; renew on time for a free assessment.

Prep takes

  1. Split time like the blueprint. Agentic Architecture is 27%, but Claude Code Config and Prompt Engineering are 20% each; MCP plus Context Management make up the rest. Don't spend 80% on agents alone.
  2. Judgment, not trivia. Objectives are tradeoffs: prompt vs. hook, plan mode vs. direct execution, batch vs. real-time, escalate vs. resolve.
  3. Build things. The guide's prep section is hands-on: agent loop, Claude Code on a real repo, MCP tools with structured errors, extraction pipeline.
  4. Know what's out of scope. Fine-tuning, vision, computer use, streaming, cloud provider configs, prompt caching internals: not tested.
  5. Write your own practice questions. You sign an NDA; don't hunt for "real" questions. Use published objectives, like the prompts below.

How to use the prompts: attach the official v1.0 exam guide PDF to a Claude chat or Project, then paste a prompt. Every prompt treats the guide as source of truth.

Integrity: These prompts produce original practice material from published objectives. They don't reproduce real exam content. You agree to an NDA before the exam starts.

Workshop: Day 1 (hands-on)

Four hours, in person and on Teams. You build a Claude Code customer service agent for Malmberg's Marinated Meats (a fictional company), one exam domain at a time. It mirrors the exam's Customer Support Resolution Agent scenario. Remote? Follow along on this page and post "Build N done" or your blocker in the Teams chat.

Before you arrive

  1. Install Claude Code and sign in. Install Python 3.10 or newer.
  2. Download the Customer Service Agent starter and unzip it.
  3. In the unzipped folder, run pip install -r requirements.txt, then python mcp_server/test_server.py. It prints ok.
  4. Run claude in that folder and accept the "trust this folder" prompt. Type /mcp: malmberg shows as connected.
  5. Download the exam guide from your Partner Academy course page. Every prompt on this page assumes you attach it.

MCP won't install? Tell Claude: "The MCP server is unavailable. Read customers and orders from data/*.json directly and follow the same rules." You can still do every build except Build 2.

Domains run in build order, not weight order. Study time should still follow the weights.

Build 1: Claude Code configuration

  1. Fill the Commands section of CLAUDE.md with exact invocations.
  2. Fill .claude/rules/mcp-tools.md: a paths glob that matches only the MCP server code, plus your tool-writing conventions.
  3. Turn .claude/skills/example-skill/ into an order-lookup skill. The description says what it does, when to use it, and when not to. Set allowed-tools.
  4. Try it: ask Claude to edit data/orders.json. The deny rule blocks it. Run /memory to see which memory files are loaded.

Check my work: Build 1

Act as a CCA-F examiner. Review CLAUDE.md, .claude/settings.json, .claude/rules/mcp-tools.md, and my skill in .claude/skills/. Is CLAUDE.md short, imperative, and does it list exact commands? Does the rule's paths glob match only the files it should? Does the skill description say what, when, and when not? Should anything in CLAUDE.md move to a rule or a skill? List the gaps and the task statement each maps to (3.1-3.3). Don't fix anything.

Build 2: Tool design & MCP

  1. Ask Claude: "Where is order MM-1002?" and "What email is on Dana Whitfield's account?" Watch which tool it picks.
  2. In mcp_server/server.py, rewrite the get_customer and lookup_order descriptions: inputs, example requests, edge cases, and when to use the other tool.
  3. Ask about order MM-1009. It fails with a generic "Operation failed". Make it a structured error with errorCategory and isRetryable; process_refund shows the pattern.
  4. Ask Claude to read the malmberg://policies/refunds resource. Restart Claude Code after editing the server.

Check my work: Build 2

Act as a CCA-F examiner. Read mcp_server/server.py and .mcp.json. From the descriptions alone, could a model reliably choose between get_customer and lookup_order? Is the MM-1009 failure a structured error a model could act on (category, retryable, message)? Is "no order found" still a valid empty result rather than an error? Is the server scoped at project level, with no secrets in the file? List the gaps and the task statement each maps to (2.1, 2.2, 2.4). Don't fix anything.

Build 3: Agentic architecture

  1. Turn Subagent.md into escalation-investigator.md: when to delegate to it, the fewest tools it needs, a model, and a handoff summary as the return.
  2. Fill Hook1.md (block refunds over $500, point Claude to escalate_to_human) and Hook2.md (block a refund unless the order belongs to the customer). Then ask Claude to implement both as PreToolUse hook scripts and wire them into .claude/settings.json. Read what it wrote.
  3. Turn Slash.md into process-refund.md. Decide disable-model-invocation and allowed-tools.
  4. Prove it: "Refund $650 on MM-1003 for customer C-002" is blocked by your hook. "Refund $20 on MM-1001 for dana.w@example.com" triggers the ask prompt.

Check my work: Build 3

Act as a CCA-F examiner. Review .claude/agents/, .claude/commands/, .claude/hooks/, and .claude/settings.json. Which business rules are enforced deterministically (hook or permission) and which rely only on the prompt? Can anything with a real side effect be invoked by the model on its own? Does the subagent have only the tools it needs, and does it return a handoff a human could act on without the conversation? List the gaps and the task statement each maps to (1.3-1.5, 3.2). Don't fix anything.

Build 4: Prompting & structured output

  1. Run python scripts/triage.py data/tickets/ticket-03.txt. The schema forces values the ticket doesn't have.
  2. Fix the three flaws in schemas/ticket_triage.schema.json: what happens when there's no order number, a category you didn't plan for, or a ticket you can't classify?
  3. Fill schemas/triage_prompt.md: explicit criteria instead of "be accurate", plus 2-3 examples for the ambiguous tickets.
  4. Run all four tickets. ticket-03 should return a null order_id; only ticket-01 should set customer_requested_human.

Check my work: Build 4

Act as a CCA-F examiner. Review schemas/ticket_triage.schema.json, schemas/triage_prompt.md, and scripts/triage.py. Will the schema push the model to invent values a ticket doesn't contain? Is there a way out for unplanned categories and for tickets that can't be classified? Are my criteria specific and checkable? Do my examples cover the ambiguous cases? What does the schema guarantee, and what can still be wrong? List the gaps and the task statement each maps to (3.6, 4.1-4.3). Don't fix anything.

Build 5: Context & reliability

  1. Fill Escalation criteria in CLAUDE.md, with 2-3 short examples of escalating versus resolving.
  2. Fill Case facts: a block of customer ID, order IDs, amounts, dates, and what the customer expects, repeated at the top of every handoff.
  3. In your order-lookup skill, keep only the order fields that matter. Never surface internal_margin_pct or picker_id.
  4. Test with the tickets. ticket-01 escalates right away. ticket-04 asks which Sam Ortega. ticket-03 escalates because the policy doesn't cover price matching. Run /compact, then ask for the case facts: the amounts are still there.

Check my work: Build 5

Act as a CCA-F examiner. Review the Escalation criteria and Case facts sections of CLAUDE.md, my order-lookup skill, and the Returns section of my subagent. Would the agent escalate at once when a customer asks for a human? Ask for another identifier when two customers match? Escalate when the policy is silent? Would amounts, dates, and order IDs survive summarization and /compact? Are verbose tool results trimmed? List the gaps and the task statement each maps to (5.1, 5.2). Don't fix anything.

Wrap-up: score yourself

Install the cert readiness assessment skill and run it on your starter folder. Expect a low Agent SDK score: today's build is Claude Code configuration, not SDK code. That gap is a good Day 2 goal.

Workshop: Day 2 (office hours)

Two hours to build your own agent, with feedback. Bring a use case. The goal is to apply Day 1's patterns to your own problem.

Starter ideas

  • IT ticket handler: triage tickets to a schema, look up assets, escalate outages.
  • MarketingHub agent: brand-voice skill, campaign brief command, approval hook before anything is published.
  • Your own: one task you did this week with a clear "done" and a step that needs a human.

How

  1. Copy the starter. Replace data/ and the tools in mcp_server/server.py with your domain.
  2. Run the five builds again in your domain: CLAUDE.md and rules, tools with structured errors, a hook for the rule that must never break, a schema, escalation criteria.
  3. Run the assessment skill at the start and at the end. Compare.
  4. Stretch: an Agent SDK loop. Paste Prompt 6: Lab Coach with Preparation Exercise 1.

After the workshop: Prompt 1 for a study plan, then Prompt 7 for a full mock exam.

Cert readiness assessment skill

Read-only Agent Skill for any coding agent that loads SKILL.md files. It scores your repo against all five CCAR-F domains (weighted like the blueprint) and returns a structured report in chat—after you add CLAUDE.md, MCP, Agent SDK code, or similar cert-relevant artifacts.

  1. Download SKILL.md
  2. Install: create claude-cert-assessment/SKILL.md under your agent's personal skills directory (path depends on the product—e.g. ~/.cursor/skills/, ~/.claude/skills/, or whatever your docs call the skills folder).
  3. In chat, ask to assess or audit the project against CCAR-F readiness (attach the exam guide PDF if you want scope anchored to v1.0).

The assessor never edits your repo. It only inspects and reports.

Prompt pack

Before you start: attach the official v1.0 exam guide PDF to the chat. Replace anything in [brackets].

Prompt 1: Build My Study Plan

Use first. Turns the blueprint into a plan based on your own gaps.

I'm preparing for the Claude Certified Architect – Foundations exam (CCAR-F). Use the attached exam guide as your only source of truth for scope.

1. List the 5 domains with their weights and the task statements under each.
2. Have me rate myself 1–5 on each task statement, one domain at a time. Wait for my answers before moving on.
3. Build a [4]-week plan at [5] hours per week. Weight time by domain weight × my gap. Include hands-on work from the guide's Preparation Exercises, not just reading.
4. End with the 3 task statements I should start on this week and why.

Prompt 2: Scenario War Room

Practices scenario-based judgment the exam is built around.

Act as a principal architect reviewing my design. Use [Scenario #] from the attached guide (or pick one at random). Set up the production context in 3–4 sentences, then give me one design decision to make.

After I answer, critique it. Tell me the tradeoff I made, what breaks in production, and which task statement it maps to. Make each round harder than the last. After 5 rounds, summarize my weak spots and what to review.

Prompt 3: Spot the Anti-Pattern

Based on the task statements in the attached guide, write 5 short, realistic snippets. Mix them up: an Agent SDK loop, an MCP tool definition and error response, a CLAUDE.md or .claude/rules file, a CI command, and a JSON schema. Each should contain one subtle mistake an architect should catch.

Show them one at a time. I'll name the flaw and propose a fix. Then give me your answer and the reasoning, and cite the task statement it tests.

Prompt 4: The Tradeoff Matrix

From the attached guide, pull out every "X vs. Y" decision the exam tests. For example: prompt instructions vs. programmatic hooks, plan mode vs. direct execution, Message Batches vs. synchronous calls, tool_choice auto vs. any vs. forced, project vs. user scope, escalate vs. resolve.

Build a table with 4 columns: the decision, when to choose X, when to choose Y, and the clue in a question that should tip you. Then quiz me with 10 one-line situations and I'll make the call.

Prompt 5: Teach It Back

I'll explain Task Statement [#] from the attached guide in my own words, as if I'm teaching a new teammate. Grade me against that task statement's "Knowledge of" and "Skills in" bullets. Tell me what I got right, what I missed, and what I got wrong. Then ask me 2 follow-up questions that dig into the gaps.

Prompt 6: Lab Coach

Turn Preparation Exercise [1–4] from the attached guide into a step-by-step lab I can finish in [2 hours]. For each step, tell me what to build, what "done" looks like, and which exam concept it proves. Don't write the code unless I ask. Give me hints first and let me get stuck a little.

Prompt 7: Full Mock Exam

Write an original practice exam that follows the format in the attached guide. Pick 4 of the 6 scenarios at random and write 15 questions for each, 60 total. Mix multiple-choice and multiple-response items, and have each item say how many answers to select. Spread questions across domains by their published weights. Write new questions. Don't reuse the guide's sample questions.

Give me one question at a time and don't reveal any answers until I finish. At the end, give me a score report like the real one: overall % correct, % correct by domain, and the task statement behind every miss.

Prompt 8: Rapid-Fire Recall

Use only the Appendix of the attached guide (Technologies and Concepts, plus In-Scope Topics). Run a 15-minute rapid-fire drill with one short question at a time. Cover things like stop_reason values, tool_choice options, Message Batches limits, the CLAUDE.md hierarchy, skill frontmatter, and the -p / --output-format json flags. Keep track of my misses and ask them again at the end.

Domain notes and instructor prompts below update hoeem's public “Claude Architect” course. Start from his originals (linked under Resources); this page revises wording, weights, and objectives for Anthropic's v1.0 CCAR-F exam guide.

27% Agentic Architecture & Orchestration

Principles

  • Reject on sight: parsing natural language for loop termination, arbitrary iteration caps as the primary stop, and assistant text as completion indicator; use stop_reason.
  • Subagents do not share the coordinator's memory; pass context explicitly.
  • Financial or security-critical flows need programmatic enforcement (hooks, prerequisite gates), not prompt-only guidance.

Patterns

  • Hub-and-spoke orchestration; trace failures to the coordinator's decomposition.
  • PostToolUse normalization; tool-call interception for policy blocks.
  • Multi-pass decomposition for large code reviews; fork_session vs resume vs fresh start with summary injection.

Domain instructor prompt

You are an expert instructor teaching Domain 1 (Agentic Architecture & Orchestration) of the Claude Certified Architect (Foundations) certification exam. This domain is worth 27% of the total exam score, making it the single most important domain.
Your job is to take someone from novice to exam-ready on every concept in this domain. You teach like a senior architect at a whiteboard: direct, specific, grounded in production scenarios. No hedging. No filler. British English spelling throughout.

EXAM CONTEXT
The exam uses scenario-based multiple choice. One correct answer, three plausible distractors. Passing score: 720/1000. The exam consistently rewards deterministic solutions over probabilistic ones when stakes are high, proportionate fixes, and root cause tracing.
This domain appears primarily in three scenarios: Customer Support Resolution Agent, Multi-Agent Research System, and Developer Productivity Tools.

TEACHING STRUCTURE
When the student begins, ask them to rate their familiarity with agentic systems (none / built a simple agent / built multi-agent systems). Then adapt your depth accordingly.
Work through the 7 task statements in order. For each one: explain with a production example, highlight exam traps, ask 1-2 check questions, connect to the next task statement.
After all 7 task statements, run a 10-question practice exam on the full domain. Score it, identify gaps, and revisit weak areas.
End with a build exercise: coordinator + two subagents, structured metadata in context passing, a programmatic prerequisite gate, and a PostToolUse normalisation hook.

18% Tool Design & MCP Integration

Principles

  • Tool descriptions are the primary mechanism for tool selection: fix vague/overlapping descriptions before classifiers or consolidation.
  • Structured MCP errors: transient vs validation vs business vs permission; don't retry valid empty results.
  • Scope ~4–5 tools per agent; know tool_choice: auto, any, forced.

Patterns

  • Project .mcp.json vs user config; ${ENV} expansion for secrets.
  • Community MCP servers before custom builds; MCP resources for catalogs.
  • Grep (contents) vs Glob (paths); Edit with Read+Write fallback.

Domain instructor prompt

You are an expert instructor teaching Domain 2 (Tool Design & MCP Integration) of the Claude Certified Architect (Foundations) certification exam. This domain is worth 18% of the total exam score.
Your job is to take someone from novice to exam-ready on every concept in this domain. You teach like a senior architect at a whiteboard: direct, specific, grounded in production scenarios. No hedging. No filler. British English spelling throughout.

EXAM CONTEXT
Scenario-based multiple choice. Passing score: 720/1000. This domain appears primarily in: Customer Support Resolution Agent, Multi-Agent Research System, and Developer Productivity Tools scenarios.
The exam favours low-effort, high-leverage fixes as first steps. Better tool descriptions before routing classifiers. Scoped access before full access. Community servers before custom builds.

TEACHING STRUCTURE
Ask the student about their experience with MCP and tool design (none / used MCP tools / built MCP servers). Adapt depth accordingly.
Work through 5 task statements in order. For each: explain with production example, highlight exam traps, ask check questions, connect to next statement.
After all 5, run a 7-question practice exam. Score and revisit gaps.
Build exercise: 3 MCP tools with one intentionally ambiguous pair, four error categories, .mcp.json with env expansion, forced tool_choice for the first step.

20% Claude Code Configuration & Workflows

Principles

  • CLAUDE.md hierarchy: user (~/.claude/) vs project (.claude/ or root) vs directory; team standards belong in project-level, version-controlled files.
  • Path-specific .claude/rules/ with glob frontmatter beats directory-only CLAUDE.md for cross-repo conventions.
  • Plan mode for multi-file/architectural work; direct execution for narrow fixes; skills vs always-on CLAUDE.md.

Patterns

  • Skill context: fork for noisy analysis; CI needs -p and often --output-format json.
  • Independent review instance beats self-review in the same session.
  • Concrete I/O examples beat vague prose for iterative refinement.

Domain instructor prompt

You are an expert instructor teaching Domain 3 (Claude Code Configuration & Workflows) of the Claude Certified Architect (Foundations) certification exam. This domain is worth 20% of the total exam score.
Direct, practical teaching. British English spelling throughout.

EXAM CONTEXT
Scenario-based multiple choice. This domain appears primarily in: Code Generation with Claude Code, Developer Productivity Tools, and Claude Code for CI/CD scenarios.
This domain is configuration-heavy: you either know where files go and what options do, or you do not.

TEACHING STRUCTURE
Ask about Claude Code experience (never used / use it daily / configured it for a team). Adapt depth.
Work through 6 task statements. For each: explain, highlight traps, check questions, connect. After all 6, run an 8-question practice exam.
Build exercise: CLAUDE.md hierarchy, .claude/rules/ globs, a skill with context: fork, CI script with -p and JSON output.

20% Prompt Engineering & Structured Output

Principles

  • Explicit categorical criteria beat vague "be conservative" instructions.
  • Few-shot (2–4) with reasoning on ambiguous cases beats more prose.
  • tool_use + JSON schema fixes syntax, not semantics: nullable fields and "unclear"/"other" enums reduce fabrication.

Patterns

  • Validation-retry works for format/structure errors, not missing source data.
  • Message Batches: cost/latency tradeoff; no multi-turn tool calling in one batch request.
  • Multi-instance review and multi-pass file + integration analysis.

15% Context Management & Reliability

Principles

  • Persistent "case facts" block for transactional data: don't summarise away amounts, dates, IDs.
  • Escalate when the customer asks for a human, policy gaps, or inability to progress, not on sentiment alone.
  • Propagate structured errors with partial results; don't silently succeed on empty or kill the whole workflow on one failure.

Patterns

  • Key summaries at the start of long context; trim tool results to needed fields.
  • Scratchpads, /compact, subagent delegation for codebase exploration.
  • Claim–source mappings through synthesis; annotate conflicts instead of picking arbitrarily.
